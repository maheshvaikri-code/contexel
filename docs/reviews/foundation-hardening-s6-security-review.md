# Security review (G5): Slice 6, honest benchmarks

Branch `feat/hardening-s6-honest-benchmarks` at `798ffef` against `main` `eddb5c3`. Reviewer: Security Reviewer (holds the ship veto). Method: every probe ran on a `git archive` copy in a scratch directory; the repository, its index and HEAD were not touched; the benchmark commands and `--write` were not run in the repository; no network call was made.

**Verdict: APPROVE WITH CONDITIONS.** The dataset check fails closed in every case tried. Nothing is read, shaped or published from a file that failed verification, and no test or module touched the network or wrote outside its temporary tree. One security tradeoff remains: ruling S6-5's parse-before-verify window is open on an unbounded `pyarrow` and on URLs taken from the listing response without a scheme or host check. Under section 5 only the human can accept that risk, or the small hardening below closes most of it.

**Conditions (one of the two before release):** C1: the human records explicit acceptance of the S6-5 residual risk (with an expiry or a follow-up). C2: apply the smallest hardening instead: a `pyarrow>=14.0.1` floor in the `benchmarks` extra, an https and `huggingface.co` check on the listed URLs, and reading the pin before downloading.

## Findings

### MEDIUM
**M1. The parquet is parsed before anything is verified, on an unbounded pyarrow and unvalidated URLs** (`benchmarks/fetch_dataset.py` `_download_rows`, `pyproject.toml` benchmarks extra). `_download_rows` follows every URL in the listing response with no scheme or host check (plain `http://` and any host are accepted; `requests` accepts only http and https, so `file://` is not possible), reads the whole body with no size cap (`timeout=600` is per socket read, not a total limit) and calls `pq.read_table` on those bytes; the digest of the derived JSONL is only checked after parsing. The extra declares `pyarrow` with no lower bound; pyarrow 0.14.0 to 14.0.0 is affected by CVE-2023-47248 (deserialization in the IPC and Parquet readers allows arbitrary code execution; fixed in 14.0.1) and pip keeps an already-installed old pyarrow. Someone who controls the Hugging Face API response, the CDN behind the redirect or the dataset's parquet conversion could reach code execution (old pyarrow) or an out-of-memory condition before the check runs; with a current pyarrow the realistic worst case is a parser crash or memory and CPU exhaustion, after which the derived JSONL fails verification and nothing is published from it. Mitigating facts: TLS verification is on (`requests` default; `verify=` never passed); the path is opt-in (benchmarks extra), runs only when the cache is absent, is never run by CI and is not part of the shipped library; the request code is not new in this slice (the diff only adds verification around it) and the CHANGELOG states the window honestly; the installed pyarrow (18.0.0) is not affected. Smallest fixes, in order of cost: (1) `pyarrow>=14.0.1` in the extra; (2) require an https scheme and the `huggingface.co` host before following each listed URL, and require the listing to be a bounded list of strings; (3) call `expected_digest()` before `_download_rows()` so a bad pin fails before the download; (4) `stream=True` with a byte cap; (5) follow-up: pin the digest of the parquet bytes before parsing (needs one download; pinning a parquet revision in the URL would make the content immutable).

### LOW
**L1. Quadratic regex backtracking in the number check** (`benchmarks/publish.py`: `RECORDS`, `EPISODES`, `BUDGET` capture `([\d,]+)` with no anchor before it; `UNIT_NUMBER` can start again after every comma). A long run of digits, or of `1,1,1,...`, in one of the four documents makes `check()` and the CI test run take minutes to hours (polynomial, not exponential). Timing of the full check with a payload appended to README.md: real documents 18 ms; 5 MB of prose 858 ms; 5 MB of `1.` runs 1,571 ms; an 8 KB `1,` run 3,943 ms; 16 KB 15,939 ms; 32 KB 64,493 ms; a 32 KB digit run 34,505 ms. Estimates at 1 MB: `UNIT_NUMBER` on `1,1,1` about 18,900 s; the records/episodes claims on digits about 4,700 s; the budget claim about 3,000 s; `HTML_CELL` on an unclosed `<td>` about 880 s; the tag strip on `<<<` about 440 s; `URLISH` on an unclosed `](` about 195 s; `BLOCK` on unclosed start markers about 180 s. Spaces, pipes, prose, `1.` runs and unclosed `href="` or `title="` stay linear. The input is maintainer-controlled repository content, hence LOW. Fix checked in a scratch copy: prefix the three claim captures with `(?<!\d)(?<!\d,)` and add `(?<!\d,)` to the `UNIT_NUMBER` lookbehinds: the integrity tests still passed (67) and the 32 KB `1,` run dropped from 64,493 ms to 34 ms; optionally refuse documents over 1 MB.

**L2. The `.part` file is left behind on failures other than a checksum mismatch** (`fetch_dataset.py`, `fetch`). The `try` covers only `verify` and catches only `DatasetChecksumError`. With the download stubbed: a mismatch leaves no partial file; a lone surrogate (encode error), a non-JSON value (TypeError), a KeyboardInterrupt in verify and an OSError in verify all leave `<name>.part`. The leftover is never used (`load()` and `fetch()` read only the cache path; a stale `.part` is truncated and re-downloaded; `benchmarks/data/` is git-ignored including the `.part`), but the inline comment "never leave an unverified file behind" overstates it. Fix: wrap the write and the verify in `try: ... except BaseException: partial.unlink(missing_ok=True); raise`.

**L3. The Markdown generated blocks do not escape values from the JSON; the HTML blocks do** (`publish.py`, implementation and shaper names, the dependency count). A poisoned JSON written through `write()` produced escaped output in both site pages and raw markup in the README (a `|` breaks the table, and a block marker inside a name confuses the block parser; `check()` then fails, which is fail closed). GitHub sanitizes README HTML, the site is published from escaped blocks, and the names come from code constants in the committed JSON. Fix: escape `|`, `<` and `>` in Markdown cells, or restrict names to a fixed character set.

**L4. The pin parser takes the first token and ignores the rest** (`fetch_dataset.py` `expected_digest`, and the same parse in `publish.py`). A pin file whose first line is a wrong digest and whose second line is the real one is accepted with the first. Not a bypass (anyone who can edit the pin can set any digest) but a clarity problem for reviewers of the pin. Fix: require exactly one line `^[0-9a-f]{64}  <the cache file name>\n?$`.

### INFO
- **I1.** With sockets blocked the only `socket.socket()` call in the tests is urllib3's IPv6 capability probe (when `llama_index.core` imports `requests`); it neither connects nor resolves a name.
- **I2.** `--write` follows symlinks and writes non-atomically. Only a target that contains a known block marker is rewritten; the relative paths are constants so `..` and absolute paths cannot occur; a root without the files raises `FileNotFoundError` (exit 1) and writes nothing; `benchmarks` is imported from the tool's own tree, never from `--root`. Fix: refuse a symlink or a path that does not resolve under the root; write through a temporary file and `replace`. (Symlink creation failed in the reviewer's environment, so this is reasoned from the code.)
- **I3.** The check only guards "documents equal the JSON"; the JSON is the trust anchor and no CI job re-runs the benchmark. Forms the scan does not catch: `12 µs`, `12 us`, `12 ns`, `1.2 s`, `1.2 sec`, `three times faster`, `3-fold faster`, `97 pct`, `recall of 97 out of 100`, `x3 faster`. Caught: `12 ms`, a number split by an HTML comment, numeric entities, full-width digits, `40 %`. The CHANGELOG discloses the unit-based scope; the `publish.py` module docstring ("a hand-typed number cannot slip in") overclaims.
- **I4.** The recorded dataset digest in COMPARISON.json is copied from the pin, not from what `verify()` returned; equivalent today because `load()` verified against the same pin.
- **I5.** `fetch()` verifies and `load()` reopens the file; only a local attacker could use the gap.
- **I6.** The measured pass in `opcount` runs on the caller's sample; none of the six implementations mutates it today. A step returning a lazy generator, or a library implemented in C, counts as glue (a measurement bias, not security).
- **I7.** `benchmarks/suites.py` downloads the tiktoken `cl100k_base` file on a cold cache during `python -m benchmarks` (pre-existing, not in this diff); "only `_download_rows` touches the network" holds for this slice's code and tests, not for the benchmark command on a cold cache.
- **I8.** The README's "refuses it unless its SHA-256 equals the digest" is accurate for the derived, LF-read JSONL only; a plain `sha256sum` of an older CRLF cache does not equal the pin (the CHANGELOG discloses this).
- **I9.** A structurally malformed COMPARISON.json makes `check()` raise `KeyError` instead of reporting a problem; it still exits 1.

## Answers
1. **fetch_dataset:** every malformed or missing pin fails closed (missing, empty, whitespace only, short, long, upper case, BOM, non-ASCII, UTF-16, a directory, NUL after the digest, digest glued to the name); a mismatch raises before anything is read and `load()` is the only reader of the cache, always through `verify()`. Line-ending tricks do not verify: an exact LF file, an all-CRLF file and a mixed file pass (the canonical file with an optional CR before each LF; `json.dumps` always escapes CR and LF inside strings so the normalization cannot change content, and `load()` parses all three identically); no trailing newline, an extra trailing LF or CRLF, a blank line in the middle, lone CR terminators, a lone CR at the end, CRCRLF, a trailing space and a BOM all fail. The digest is `hashlib.sha256`, a 64-character lower-case string compared with `!=` against a regex-validated lower-case string. The real cache's digest equals the pin.
2. **Parse-before-verify:** see M1 (TLS on, timeouts per read, redirects followed as the CDN needs, no size cap, no host check). Acceptable for an opt-in benchmark path only with C1 or C2.
3. **publish and the check tool:** no `eval`, `exec`, `pickle`, `yaml` or shell use on document text; an audit hook during `check()` saw no writes and no socket or subprocess events; regex timings: L1; `--write` confinement: I2; escaping: L3.
4. **opcount and imports:** the profiler is restored after an exception, a KeyboardInterrupt, a generator step, a step that clears the profiler and a thread; the warm-up runs once on a deep copy of the fixed synthetic sample, never on real data; importing `competitors`, `publish`, `opcount` and `fetch_dataset` reads nothing but code and writes nothing.
5. **Network and filesystem:** with sockets blocked in process, the six new test files gave 111 passed, 1 skipped (the skip is the local-cache test); with a `sitecustomize` block that also covers subprocesses, the same; the positive control was blocked; no writes outside the temporary base; `requests` appears only in `fetch_dataset.py`. A grep of the added lines for drive or home paths, AppData, user names, e-mails, key or token shapes and private keys found nothing; commit bodies clean; the generated JSON environment holds only the Python version, `Windows (AMD64)` and library versions.
6. **Supply chain and licensing:** `git diff main..HEAD -- pyproject.toml` is empty, no dependency added; the benchmarks extra is optional and CI installs only `.[dev]`; the docs make no licence claim for the data and it is not redistributed (`benchmarks/data/` is git-ignored); an attribution line for the CodeSearchNet authors would be a courtesy.
7. **Other integrity gaps:** I3, I4 and the loaded-machine timings; all disclosed or low-impact; none is a disabled check.

## Could not verify
`pip-audit` (network off limits); a real download and whether it reproduces the committed digest; the Hugging Face redirect hosts and the dataset card's licence field; symlink behaviour of `--write`; which tiktoken version introduced its BPE hash check; behaviour on Python 3.9 to 3.11, Linux or macOS (only 3.12.7 on Windows was run); the attribution of Python processes running on the machine (the process listing was denied by the permission classifier and not worked around).

## Outcome after the fix waves (filed with the branch)

Re-reviewed at `53246a8` (two scoped re-reviews). **Sign-off: APPROVE WITH CONDITIONS.**

- **M1 / condition C2:** applied instead of asking the human to accept the residual risk: `pyarrow>=14.0.1` in the `benchmarks` extra (the only `pyproject.toml` change), the listing is checked before any listed URL is requested (at most 64 strings; each must fully match `https://huggingface.co/[A-Za-z0-9._~%/-]+`, which refuses userinfo, ports, backslashes, whitespace and control characters; an earlier version that judged the host with `urllib.parse` could be bypassed by a backslash URL, which the first re-review found and the second wave closed), and the pin is read before anything is downloaded. Redirects that Hugging Face answers with are followed; the download has no size cap and the digest of the parquet file is not pinned, so the file is still parsed before the derived JSONL is verified (recorded follow-up; the CHANGELOG says so).
- **L1** (quadratic patterns): every pattern of `publish.py` measured at most 0.33 s on 160,000-character adversarial inputs and 0.46 s on a 1 MB mixture. **L2** (`.part` left behind): removed on any exception. **L3** (Markdown cells unescaped): escaped, generated output byte-identical on the committed data. **L4** (lax pin parser): the pin must be exactly one line. **I2** (`--write`): refuses symlinks and targets outside the root, writes through a temporary file and replaces it. **I3** (docstring overclaim) and **I4** (digest recorded from `verify()`): fixed.
- **Not changed (recorded):** I1, I5, I6, I7, I8, I9 as described above.
- **New LOW findings of the re-review, recorded as follow-ups:** `unicodedata.normalize("NFKC")` is quadratic on some characters (about 110 s for a 2 MB published file of one such character; it fails closed and needs a contributor-authored file); the catch of malformed results also wraps the text scan (an `&#` followed by more than 4,300 digits is reported against the results file, and a programming error in the scan would be reported as malformed results); deeply nested results JSON raises `RecursionError` (a traceback, non-zero exit).
- **Conditions that remain:** the human regenerates the `COMPARISON` and `RESULTS` timings on a quiet machine before merge; the parquet digest and the download size cap stay follow-ups.
