## How this plan is organized (and why it is not one giant document)

The work is seven slices across three languages. A single plan with finished code for all of them would have to describe TypeScript and C# internals that depend on what the earlier slices change, so it would contain invented code. Instead:

1. **This master plan** fixes the slice order, the files each slice touches, the tests that prove each acceptance criterion, risks and rollback points.
2. **Slice 1 has a complete bite-sized plan, written and verified now:** `docs/superpowers/plans/2026-11-19-foundation-hardening-s1-safety-net.md`. Its code was executed in scratch copies before it was written down (results recorded at the bottom of that file).
3. **Each later slice gets its own bite-sized plan, written from the code as it stands when the previous slice lands,** and shown to the human before that slice starts. A slice plan is never started on a tree it was not written against (its Task 0 checks the baseline counts).

## Execution rules (apply to every slice)

- **Branch per slice:** `feat/hardening-s<N>-<slug>`, from a clean `main`. Merge to `main` only after G4 and G5 pass and the human says so. **Never push.**
- **One commit per task** (Conventional Commits, ≤ 72 chars). Author = the repo's configured identity. **No `Co-Authored-By` trailer** (project owner's standing rule, which overrides the harness default). No version bump on a task commit; unreleased work accumulates under `[Unreleased]` in `CHANGELOG.md`.
- **Inner loop** (`skills/loop-engineering.md`): anchor to one AC verbatim → smallest change → run and paste real output → mechanical gate → decide. Budget 10 iterations per criterion (Class L); thrash rule applies (same file edited 3× with no test delta, or the same error twice → go up a level).
- **Regenerate vectors against the checkout, never an installed package:** `python parity/generate_vectors.py` puts `parity/` (not the repository root) first on `sys.path`, so without an editable install it silently imports an INSTALLED `contexel` (this machine has a stale 0.1.17) and can write wrong vectors. Run it as `PYTHONPATH=<repo root> python parity/generate_vectors.py` (or after `pip install -e .`, as CI does) and check with `python -c "import contexel; print(contexel.__file__)"` under the same environment.
- **A slice is done only when:** all three suites are green locally (this machine is Windows 11; Linux and macOS are not available here) with the counts the slice plan states, `PYTHONPATH=. python parity/generate_vectors.py && git diff --exit-code parity/vectors.json` is clean, the slice's acceptance criteria are each demonstrated by a named test, the changelog is updated, and a fresh-context `code-reviewer` (G4) and `qa-engineer` (G5) have reported with no unresolved BLOCKER/MAJOR finding. The three-OS matrix is proven by CI after the human pushes; until then it is *unverified* and reported as such.
- **New public API is documented and demonstrated (brief AC 34):** every new public stage or parameter gets its README and `site/stages.html` entry and one runnable example whose output is asserted by a test (`tests/test_doc_examples.py`, created in Slice 2 and extended by Slices 4 and 5; TypeScript and C# examples live in their existing test projects). Every behavior change appears in the changelog under "Behavior changes".
- **Stop-and-ask triggers** (§5): any change to a public contract not in the design; a fuzz divergence that cannot be fixed or recorded as a margin; a dependency not already approved; anything that needs the network or a credential; an AC that proves wrong when tested.
- **Tests are never weakened to go green.** A failing golden fingerprint or vector means the behavior changed; either fix the code or open an ADR amendment.
- **The single permitted edit to existing test expectations** in the whole sub-project: the `allowlist_bool_int` vector (Slice 2) and the C# `Throws`→`ThrowsAny` assertions (Slice 2), both named in brief AC 9.

## Threat sketch (Class L)

- **Assets:** the integrity of the two security controls (`allowlist`, `quarantine`); the truthfulness of the audit trail (fingerprints, dropped ids); the parity vectors (the specification of record); the release pipeline and version identifiers.
- **Entry points / untrusted inputs:** tool-output records and their nested values; **caller-supplied regex** in `quarantine(patterns=…)` (unchanged risk: catastrophic backtracking stays the caller's responsibility, now documented next to the new compile-time validation); the large-text input to `split` (a 1,000,000-character test pins linear behavior); the benchmark dataset download (Slice 6 adds a SHA-256 check); generated fuzz corpora (generated in CI from fixed seeds, never fetched).
- **Worst plausible abuse:** (a) crafted text that evades `quarantine` by hiding the phrase in a nested value with a newline, or by `True`/`1` type confusion in `allowlist` — both fixed and regression-tested in Slice 2; (b) a policy that changes behavior after its fingerprint was recorded — closed in Slice 3; (c) a stale or wrong version going out through a mismatched release — Slice 3's CI version check; (d) resource exhaustion through huge inputs to the new stages — bounded by linear algorithms and the million-character test.
- **Security Reviewer sign-off** is required at G5 for Slices 2, 3 and 6 (controls, audit, dataset integrity).
