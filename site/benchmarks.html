Benchmarks

What was measured, how, and where it stops — and deliberately without a headline "X% reduction" number, because reduction is a property of your data and your budget, not of the library. Two reproducible suites; full tables live in the repo (benchmarks/RESULTS.md, benchmarks/COMPARISON.md). Every benchmark result on this page is generated, or checked against the results: the tables are rendered from benchmarks/RESULTS.json and benchmarks/COMPARISON.json, and python tools/check_benchmark_numbers.py, run in CI, fails when this page disagrees with them. CI checks against the committed results; it does not re-run the benchmarks.

The default tokenizer estimates ~4 chars/token: roughly right for typical prose and code, but it under-estimates JSON-heavy records (the JSON sample is synthetic search-hit records with hexadecimal ids; on other records the error differs), so install contexel[accurate] when budget precision matters. Inactive tracing is meant to cost next to nothing, but this suite compares it with active tracing only: an untraced baseline (the stages called without a pipeline) is not measured here. Active tracing token-counts every stage boundary and is priced accordingly.

Suite 2 — against the prior art, on real data

python -m benchmarks.competitors (needs the benchmarks extra; the first run downloads the CodeSearchNet python/test split, ~30 MB, and refuses it unless its SHA-256 equals the digest committed in benchmarks/dataset.sha256; to install the library versions that were measured, add -c benchmarks/constraints.txt, which the extra alone does not pin). The full split — 22,176 real functions — is run through simulated, overlapping substring searches into 28,047 search-tool records (almost all of the duplicates are the same function matched by several searches; a few are different functions from different repositories that share a path and a symbol), plus 100 ground-truth episodes where the record the agent needed is known and guaranteed present in the raw hits, so recall isolates shaping loss, not retrieval loss. Budget: 1,500 tokens, counted with contexel's default estimator (about four characters per token), the same one the hand-written glue uses; every cap and price, and the Fill and Useful columns, are counted with it too. The estimator is for soft budgeting: a hard limit needs an exact tokenizer (contexel[accurate] and tokens.use_tiktoken(), or the provider's own counter). Measured with an exact tokenizer, most of the contexts that fill the budget here run over the estimated budget. One corpus and one task, so read it as a measurement, not a law. This benchmark was written by contexel's author. The comparison wirings are our best effort, one dataset, 100 episodes; corrections from the maintainers of the compared libraries are welcome (open an issue).

How to read it

  • Two experiments in one table. ms @28k holds the policy constant — libraries get identical hand-written glue for whatever they lack; for langchain-core and llama-index-core most of that time is converting the records to the library's message or node type (in llama-index-core's row the only llama-index code that runs is building and unbuilding its node objects; langchain-core's one native step is trim_messages). The outcome columns (Recall / Fill / Useful) are the opposite: each library acts only through the operations this benchmark wired for it, so a different wiring can change these rows, and they do not rate the libraries at their own jobs. The task is contexel's own six stages, scored with contexel's estimator, field list and dedupe key, so it measures how much of that task each library covers in these wirings. Native ops (in this wiring) counts how many of the task's six operations (select, dedupe, rescore, truncate, rank, trim) the library performed itself in the wiring this benchmark chose. Whether a step enters the library's own code is detected automatically (benchmarks/opcount.py); which library functions each implementation uses, and which operation each step serves, are the benchmark author's choices (the step lists are in benchmarks/competitors.py). The counts therefore describe these wirings, not what each library can do. Other wirings exist and are not counted here: toolz's topk and accumulate can express a rank and a running budget cut, and llama-index-core has metadata exclusion (excluded_llm_metadata_keys), ingestion dedupe (IngestionPipeline with a docstore) and a token-limited ChatMemoryBuffer.
  • Recall says little when the context runs over the budget. toolz and llama-index-core keep the needed record by emitting many times the budget (the Fill column), in the wiring used here, which has no budget step for either. Both can be given one (toolz accumulate; llama-index-core ChatMemoryBuffer, or PromptHelper, which its response synthesizers use to fit text to the context window). llama-index-core offers related operations on its node types: a score cutoff (SimilarityPostprocessor), a score-ordered reorder (LongContextReorder), rerankers with top_n, metadata exclusion, docstore dedupe, PromptHelper truncation to the context window and a ChatMemoryBuffer token limit; this benchmark wires two of them (the score cutoff and the reorder) and counts neither as one of the six stages, and the cutoff it uses removes nothing under the strong signal. langchain-core holds the budget as the estimator counts it, but no langchain-core step in this wiring projects or dedupes the records, so part of the budget goes to duplicates and field bloat; it never reads the score, so both of its recall columns reflect the same weak per-term incoming order, and the needed record survives only when it arrives early in that order. Useful is the share of context tokens spent on needed fields of unique records: the needed fields and the dedupe key are contexel's, so a row that projects to those fields and dedupes on that key gets the full share by construction, and a context that is empty counts as fully useful by the current scoring (langchain-core returns one when its first record alone exceeds the budget).
  • ms/episode times the shaping and the scoring. It is the mean wall time per episode of the shaping plus the benchmark's own scoring of the result (one pass), so a row whose contexts are very large also pays for scoring them. contexel and the hand-written term-overlap scorer are the two slowest budget-compliant rows (every context within the budget as the estimator counts it), in an order that can change from run to run: contexel derives relevance from each record's own text (batch relevance with IDF, saturating term frequency and in-order proximity) on top of projecting, deduping on a key, clipping, ranking, and budgeting stage by stage, and the scorer does less of that record work (whole-word overlap). Both clip and price with the same estimate: contexel computes every cap with the active tokenizer, here the default of about four characters per token. Every other compliant row is faster by doing less still. All rows are noise next to one model call. The timing columns (the ms columns and Import ms) are one run of the command on one machine, and vary with the machine's load and from run to run; the other columns are deterministic. Import ms is the median of 5 fresh interpreters, each importing only the library's top-level package (interpreter start-up excluded; the modules a task uses can cost more). Transitive deps counts the installed distributions the package requires, recursively: the installed closure, with environment markers evaluated for the measuring machine and no extras.
  • The two recall columns test trust in the tool's score. The two signals differ only in the score value: the hit lists arrive in the same order under both, so a row that never reads the score has identical columns by construction. The hand-written row trusts the tool's score, so its recall tracks that score's quality. contexel's rescore replaces the tool's score with relevance derived from the records' own text, so its two columns read the same by construction, which shows that it does not depend on the tool's score. The hand-written row with its own term-overlap scorer is the fairest comparison: another rescorer, not none, with one caveat. contexel's lead over it comes from rescore's in-order proximity bonus; the episode queries keep the target's word order, which that bonus rewards, and with the bonus switched off contexel's recall on these episodes is not above the term-overlap baseline's (this benchmark does not generate that row).

Inflected queries

The episodes above query with the target's own words, so exact-word matching is never tested. A second set of episodes, chosen so that every query term can be inflected, hands the shaper deterministic inflections of those words (parse becomes parsing, returns becomes return; synthetic, the rule is in benchmarks/inflection.py), while its hit lists come from the original terms. Its target records differ from the main table's, so contexel's recall with the original terms there need not equal its recall in the main table. Exact-word matching fails by construction and match="stem" is measured (only terms the frozen stemmer maps to one stem are used, so the stem row shows the stem match carrying through ranking and the budget, not how many English inflections the stemmer covers):

Exact-word matching (the default) collapses on inflected queries, and so does the hand-written term-overlap scorer; match="stem" recovers them (for the terms the stemmer maps to one stem, which is what the episodes use). The hand-written row that trusts the tool's score never reads the query, so inflection cannot touch it: it is the control. This measures inflection robustness only — not synonyms, not paraphrase, not meaning.

Limits, stated plainly

Recall@budget has a ceiling no shaper escapes: when a query legitimately describes more records than the budget holds, some valid record is cut — semantic or not. Full recall here means the ambiguity clusters resolved once exact-word evidence and the in-order proximity bonus were used; vaguer queries, a different corpus, or a tighter budget can put it back below full recall, and that is the data's property, not the policy's.

rescore is lexical: a query saying parsing scores zero against a document saying parse unless you opt in to match="stem", a small frozen English stemmer; synonyms and paraphrase belong to semantic models (LLMLingua compression, ColBERT retrieval, cross-encoder reranking), which contexel deliberately does not compete with.

And shaping is not an injection defense: rescore ranks textual relevance — a hostile record that matches the query well ranks well, including one that says "ignore all previous instructions". contexel ships two deterministic boundary controls — allowlist (a provenance gate, the strong control) and quarantine (a pattern tripwire for the loud, literal cases; paraphrase passes it) — both traced and audited. Content authentication still belongs upstream of the contract; treat every shaped record as data, never as instructions.
